# ADR-0054: Architecture-Lint Enforcement Posture: Ratchet CI, Layer-Rule Coverage, and the Generated-Project Contract

**Date:** 2026-08-14
**Status:** Proposed
**Type:** Architecture
**Relates to:** ADR-0043 (linter derives cross-context legality from manifest `depends_on`) — this ADR does not change ADR-0043's cross-context ladder; it fixes the _layer-rules_ engine that runs alongside it and the _CI plumbing_ that runs both.

> Numbering note: the remediation plan refers to this decision as **item "ADR 0.8"**; it is filed here as **ADR-0054**. Wave-0 items 0.1–0.7 are filed as **ADR-0047 through ADR-0053** in this same batch, so this ADR takes the next contiguous slot. The highest pre-existing record was ADR-0046; the historical ADR-0009/0010 numbering collisions are not reused.

## Context

The architecture linter is real code that runs, but in host CI it enforces nothing, and even when invoked directly it is blind to three of the violation classes the 2026-08-13 review found rampant. Both facts are documented in the audit (`docs/planning/2026-08-13-architecture-review/AUDIT-2026-08-14.md`, AUD-010, AUD-011, AUD-019, all under §3). Wave 2 of the remediation plan (items 2.1/2.2/2.3, `docs/planning/2026-08-14-architecture-remediation-plan.md`) implements this ADR, and the plan places enforcement _before_ boundary remediation precisely because "fixing boundaries before fixing the fence guarantees regression" (plan §"changes four things", point 2). Three grounded observations force the decision:

1. **CI lint is advisory-only and the "verify" step verifies nothing (AUD-010).** The sync CLI defaults `strict` to `false` (`packages/sync/src/cli.ts:91`, `strict: options.strict ?? false`). With strict off, `runArchLinter` logs a linter failure and returns without throwing — the `throw new Error("Arch-linter failed in strict mode")` is gated on `strict` (`packages/sync/src/linter.ts:53-54`), so a boundary violation merges green. Worse, the workflow step named **"Verify Architectural Rules After Sync"** runs `cli sync --dry-run --allow-dirty` (`.github/workflows/sync-integrity.yml:50-51`, invoked as `yarn workspace @hexagen/sync run cli sync …`), and `--dry-run` short-circuits _before_ the linter ever runs (`packages/sync/src/linter.ts:17-20`, `if (dryRun) { logger.info("[DRY-RUN] would run arch-linter"); return; }`). The step's name asserts a check it structurally cannot perform. A silently-swallowed failure mode compounds this: the linter is spawned with a fixed `timeout: 30_000` (`packages/sync/src/linter.ts:35`) whose expiry is caught by the same non-throwing catch (`:44-56`). The `--strict` help text also over-promises: it reads "Fail on architecture linter warnings" (`packages/sync/src/cli.ts:71`), but strict only rethrows on linter _failures_, not warnings.

2. **The layer-rules engine is blind to relative-crossing, node builtins, and npm packages in domain/application (AUD-011).** In the domain branch (`tools/arch-linter/src/index.ts:351-385`), any non-`@` specifier that starts with `.` or `/` is unconditionally treated as allowed (`:352-356`), so a relative import that reaches across into a sibling layer is never inspected. For the remaining specifiers, a violation is only produced when `imp.getModuleSpecifierSourceFile()` resolves to an in-project source file (`:359-360`) — a node builtin (`node:fs`) or an npm package (`js-yaml`) resolves to nothing (or to `node_modules`, excluded at `:375`), so it slips through with no finding. The application branch is structurally similar: relative/absolute specifiers early-return as allowed (`tools/arch-linter/src/index.ts:389-394`), and the same `sourceFile`-gated check with a `node_modules` exclusion (`:398-414`) misses builtins and packages. The net effect, confirmed by the audit, is that run against the host the linter prints "Architecture is compliant." (`tools/arch-linter/src/index.ts:515`) while the review's HEX-011/012/014/027-class violations stand. One of those "violations" is legitimate: `js-yaml` is imported directly in the manifest-generation **domain** layer (`packages/manifest-generation/src/domain/services/manifest-view-data-parser.ts:1` and `manifest-violation-fixer.ts:1`). Per the HEX-026 disposition (AUDIT §2, HEX-026 row line 73; plan §"Explicitly dropped" lines 352-353), that import is an _accepted exception_: YAML text is the core domain artifact there (line-ranged, format-controlled dump), the same class as the Zod parsing the domain already does — so the new npm-in-domain rule needs an allowlist, not a blanket ban.

3. **No CI job runs any of the three firewall layers (AUD-019).** No workflow under `.github/workflows/` invokes `eslint`, `turbo run lint`, `lint:arch`, or `scripts/validate-ui-boundary.sh` (the sole `eslint` match under `.github/workflows/` is a comment in `capstone.yml` describing a fixture's dev-deps, not a lint invocation). The `sync-integrity.yml` workflow runs build, sync, typecheck, template-parity, and tests but only the swallowed `--dry-run` lint step. `scripts/validate-ui-boundary.sh` self-describes as "Layer 3 of the 3-layer information state firewall … Run in CI as part of the merge gate" (`scripts/validate-ui-boundary.sh:4,10`) — a role no workflow grants it. Enforcement today is only the bypassable pre-commit lint-staged path.

The tension the decision must resolve: turning strictness _on_ will not stay green. The AUD-011 engine fixes (plan item 2.2) surface exactly the violations Waves 5–8 then burn down (plan §"Wave 2 rationale"). A hard "any violation fails CI" gate would red-wall `main` from the first fix PR onward. And this is a **published-package** change: `tools/arch-linter` ships as `@hexagen-monaco/arch-linter`, injected into every generated project as a devDep (`packages/sync/src/generators/root-file-templates.ts:36`, `"@hexagen-monaco/arch-linter": "^{toolchainVersion}"`) with the `sync-integrity.yml` workflow (PR #330 auto-injection, per ADR-0046 Context/Extends). Whatever the linter learns to catch, generated customers inherit — so the contract change is release-gated, not a silent tightening.

## Decision

### 1. CI enforces on a ratchet, not strict-from-zero

CI fails on **new** architecture-lint violations measured against a committed baseline; the baseline **shrinks** per remediation PR and never grows. Concretely:

- A machine-readable baseline (the current known-violation set) is committed to the repo. The Wave-2.2 engine fixes produce the initial baseline (plan item 2.2 acceptance: "violations recorded as the ratchet baseline").
- Every PR runs the linter; the gate fails iff the run reports a violation **not** present in the baseline (a regression) — an added violation, or a violation in a newly-touched file.
- A remediation PR that removes a violation **must** delete the corresponding baseline entry in the same PR (plan §Wave 5, line 274: "each PR deletes its own baseline entries"). The baseline is monotone-decreasing; adding an entry to unblock a PR is disallowed by review, not tooling.
- The baseline reaching empty is the terminal state; at that point the ratchet is equivalent to strict-from-zero and the baseline file may be removed.

This is the plan's binding choice (plan §"Wave 2 rationale", lines 181-184: "CI fails on _new_ violations against a committed baseline, and the baseline shrinks per remediation PR"). Strict-from-zero is explicitly rejected: it would red-wall `main` for the duration of Waves 5–8.

### 2. The layer-rules engine gains three coverage classes, one with an allowlist

The linter (`tools/arch-linter/src/index.ts`) must report, for domain and application files, the violation classes it currently misses:

- **2a. Cross-layer relative imports.** A relative/absolute specifier that resolves _out of the file's own layer_ (e.g. a `domain/` file importing `../infrastructure/…`) is a violation. The current blanket "relative = allowed" shortcut (`:352-356` for domain, `:389-394` for application) is replaced with a resolve-and-check that classifies the target's layer.
- **2b. Node builtins in domain/application.** A `node:*` (or bare-builtin) specifier in a `domain/` or `application/` file is a violation. This is the class the `sourceFile`-gated checks (`:359-360`, `:397-398`) silently pass today because builtins have no in-project source file.
- **2c. npm packages in domain, with an allowlist.** A bare npm-package specifier in a `domain/` file is a violation **unless** the package is on an explicit per-context allowlist. The allowlist is seeded with **`js-yaml` for the manifest domain** (the HEX-026 accepted exception; AUDIT §2 HEX-026, plan §"Explicitly dropped" lines 352-353: "Documented as an accepted exception in ADR 0.8's allowlist — YAML text is the core domain artifact"). The allowlist lives with the linter's config surface (alongside `linter-config.yaml`'s existing `global_whitelist` / `package_rules`), so a project adds an exception declaratively, consistent with ADR-0043's config model. Application-layer npm packages are _not_ banned by this ADR (application is the composition/orchestration seam); only the domain gets the package ban.

This ADR does **not** touch the cross-context `depends_on` ladder decided in ADR-0043 (`tools/arch-linter/src/cross-package-violation.ts`); it repairs the _intra-package layer_ checks that run beside it. Acceptance of the coverage work is the "irony check" (plan item 2.2 delegation): the fixed linter, run against the host, reports the HEX-011/012/014/027-class violations instead of "Architecture is compliant."

### 3. CI lint honesty (the plumbing)

- Replace the misnamed `--dry-run` step (`.github/workflows/sync-integrity.yml:50-51`) with one that actually invokes the linter (either `cli sync --strict --allow-dirty` after the real sync, or a direct arch-linter invocation), so a seeded violation fails CI.
- A dedicated CI lint job runs all three firewall layers on every PR: workspace `eslint`, `scripts/validate-ui-boundary.sh`, and the arch-lint ratchet (plan item 2.3). The job is **required for merge**.
- The swallowed 30 s exec timeout (`packages/sync/src/linter.ts:35`) is raised/parametrized and, on expiry, surfaces an explicit timeout error rather than being caught by the non-throwing catch (`:44-56`).
- The `--strict` help text (`packages/sync/src/cli.ts:71`) is corrected to describe what strict actually does (fail on linter failure), removing the "warnings" over-claim.

### 4. Generated projects inherit the strengthened linter — release-gated

The layer-rule coverage of §2 is a **published-package behavior change** to `@hexagen-monaco/arch-linter`. It ships with the next npm release under the standing release-gate (plan lines 197-198: "published-package behavior change — release notes required, ships with the next npm release (release-gated, like all publishes)"). The generated-project contract changes as follows:

- Generated projects that already receive the arch-linter devDep (`packages/sync/src/generators/root-file-templates.ts:36`) and the injected `sync-integrity.yml` begin catching the new classes on their next `@hexagen-monaco/arch-linter` bump. A newly-scaffolded project that happens to have a `node:*` import in a domain file, or an un-allowlisted package, will start failing where it previously passed — this is the intended tightening, but it is a contract change and therefore requires release notes.
- The seed allowlist (§2c) is host-specific (`js-yaml`/manifest domain). Generated projects get an **empty** domain-package allowlist by default; their `linter-config.yaml` scaffold documents how to add an exception, mirroring ADR-0043's `depends_on`/`global_whitelist` model. Generated projects are not silently granted the host's exception.

## Consequences

- **Waves 5–8 land under a working fence.** Every boundary fix is protected: the ratchet catches any regression the moment it is introduced, and the "fix boundaries before the fence" failure mode (plan §"changes four things", point 2) is closed. Item 2.2's baseline is the input to Wave 5's shrink discipline (plan §Wave 5, line 274).
- **The baseline is a living artifact with a hard invariant.** Reviewers enforce monotone-decreasing: a PR may only remove baseline entries, never add. Because the enforcement is social (review) not mechanical, the baseline file must be small and human-diffable; the ratchet tooling should print, on failure, exactly which entries are new vs baseline so the regression is unambiguous.
- **One accepted exception is now first-class.** `js-yaml` in the manifest domain stops being an unflagged blind spot and becomes an _explicit_ allowlist entry — the exception is visible and auditable rather than invisible. HEX-026 is formally dropped as a codec-port work item and lives on only as this allowlist entry (plan §"Explicitly dropped" lines 352-353, Appendix A HEX-026 → "dropped (ADR 0.8)" line 385).
- **Generated customers get a stricter linter on the next release.** Because the contract tightens, the release notes must call out the three new classes and the empty-by-default domain-package allowlist, so a downstream project that legitimately imports a package in its domain knows to allowlist it rather than treat the new failure as a regression. This rides the same release-gate as all `@hexagen-monaco/*` publishes (explicit go-ahead required).
- **CI becomes a real merge gate.** After item 2.3, eslint + UI-boundary + arch-lint-ratchet run on every PR and block merge; the `validate-ui-boundary.sh` header's long-standing "merge gate" claim (`scripts/validate-ui-boundary.sh:10`) becomes true. The pre-commit lint-staged path is no longer the only line of defense.
- **No change to ADR-0043.** The cross-context legality ladder and its `shared-kernel`/`depends_on` trust model are untouched; this ADR is additive to the layer-rules engine and the CI plumbing. The frozen-context clearance ADR-0043 recorded for `tools/arch-linter` (ADR-0043 §"Frozen-context clearance", lines 88-99) continues to authorize the 2.2 engine edits.
- **Scope boundary with sibling audit items.** This ADR governs AUD-010/011/019 only. The `typecheck:test` CI gap (AUD-020) is governed by plan item 2.4 and is out of scope here.
