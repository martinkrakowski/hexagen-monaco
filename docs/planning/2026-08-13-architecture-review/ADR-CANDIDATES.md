# ADR candidates

Decisions that need an ADR **before** the related code moves. Each item is a
decision, not a refactor brief. Implement only after the ADR is accepted.

## ADR-C1 — Port single-ownership vs cloned contracts

**Context.** `export (interface|type) \w*Port` appears under 166 names. Seven
names are declared in more than one file. Three of those are real ownership
clashes (not test fixtures):

- `ManifestGenerationPort` — `execute(...)` in `@hexagen/manifest-generation`
  vs `generateTopology/generateAdapters/generateManifestPipeline` in
  `@hexagen/mcp-server` (HEX-005).
- `ProjectConfigurationReadPort` — same `getManifest()` cloned in
  project-configuration, mcp-server, and sync (HEX-006).
- `FileSystemPort` — `readFile/mergeManifests` vs `exists/mkdir/writeFile`
  (HEX-007). HEX-002 and HEX-014 will need a write/mkdir port.

AGENTS.md and generator invariants require “each port belongs to exactly one
bounded context.”

**Options.**

1. **Import the owner’s type.** Consumer packages depend on the owning
   package and do not redeclare.
2. **Rename to context-specific ports** when the contracts are not
   substitutable (the two `FileSystemPort`s).
3. **Lift a shared-kernel port** into `@hexagen/shared` only when the
   operations are truly generic (unlikely for manifest merge).

**Recommendation.** (1) for HEX-005 and HEX-006. (2) for HEX-007
(`ManifestMergeFsPort` vs `GeneratorFsPort`). Do not invent a kitchen-sink
shared `FileSystemPort` to satisfy HEX-002.

**Consequences.** mcp-server and sync gain a workspace dependency they may
already have. Homonymous types stop compiling against the wrong adapter.

**Affected findings.** HEX-005, HEX-006, HEX-007, HEX-002, HEX-014, GOD-010,
HEX-034.

## ADR-C2 — Inbound vs outbound directory convention

**Context.** Several packages park *driven* ports under `application/ports/in`
and inject them into use cases. Comments on those files say “infrastructure
adapters implement this.” Observed in security, governance,
monaco-orchestration, wizard-orchestration, and project-configuration
(HEX-018). MCP tools then depend on concrete `*UseCase` classes instead of
inbound ports (HEX-019).

Hexagonal convention in this repo (workspace.config.yaml stubs): inbound =
driving (UI/HTTP/CLI calls the use case); outbound = driven (use case calls
a port the adapter implements).

**Options.**

1. **Enforce the documented convention.** Use cases *implement* inbound
   ports; driven contracts live in `ports/out`.
2. **Accept “ports/in means the only port the use case has”** and update
   layer-rules + sync generators so the linter stops implying otherwise.
3. **Hybrid.** Keep current folders; require every port to declare
   `direction: in | out` in the context YAML.

**Recommendation.** (1). It matches AGENTS.md Domain/Adapter worker specs
and unblocks HEX-015 (use case implements inbound *and* delegates I/O).

**Consequences.** Folder moves across ~5 packages. Sync generators that emit
`ports/in` stubs with “adapter implements this” comments must change.

**Affected findings.** HEX-018, HEX-019, HEX-015, HEX-009.

## ADR-C3 — Security bounded context or fold

**Context.** `@hexagen/security` has a real port (`ISecretScanner`) and
adapter (`TuffleHogAdapter`) but is absent from
`.architecture/manifest.yaml` `bounded_contexts`, from `tsconfig.base.json`
references, and from in-repo consumers (HEX-009). Its tsconfig is Node16
and does not extend the workspace base (MOD-005).

**Options.**

1. **Register `security` as a supporting core context** and wire
   `ISecretScanner` from sync / project-generation / wizard.
2. **Fold the scanner into `@hexagen/governance`** (policy evaluation is
   already there) and delete the package.
3. **Fold into `@hexagen/shared`** as a shared-kernel port.

**Recommendation.** (1) if secret scanning is about to be called from
generation/sync. (2) if it will stay unused for another quarter — an
unwired package with a fake hexagon is worse than no package.

**Consequences.** Option 1 adds a context file, linter package_rules, and
tsconfig reference. Option 2 is a move + delete.

**Affected findings.** HEX-009, HEX-018, HEX-035, MOD-005.

## ADR-C4 — Empty hexagonal folders and frozen scaffolds

**Context.** `rg '^export \{\s*\}' packages --glob '**/src/**/*.ts'` finds
31 empty barrels, all `@generated by @hexagen/sync` or “minimum content to
prevent TS2306.” `core-domain` exports MVK from `src/mvk/v1` while
`domain/application/infrastructure` are `export {}` (HEX-025). Frozen
contexts `architectural-enforcement` and `code-generation` have no runtime
code. `transaction-system` is also `status: frozen` but *is* implemented —
do not delete it.

AGENTS.md: “Never leave a barrel with only `export {}`.”

**Options.**

1. **Stop generating unused layer folders.** Sync emits a layer only when
   the context YAML lists entities/ports/adapters.
2. **Keep folders; re-export real modules** (move MVK under `domain/`).
3. **Keep empty barrels** and repeal the AGENTS.md rule (not recommended).

**Recommendation.** (1) for frozen empty packages (remove from `packages/`
and `bounded_contexts`). (2) for `core-domain` and `runtime` (the code is
real; the folders are wrong).

**Consequences.** Sync generator change. Arch-linter must not require a
domain folder on a shared-kernel that opted out.

**Affected findings.** HEX-025, HEX-035.

## ADR-C5 — LLM fallback and provider-catalog ownership

**Context.** Vendor URLs and env-var names live in
`packages/local-llm/src/domain/cloud-provider-catalog.ts` and
`packages/agentic-interaction/src/domain/provider-config.ts` (HEX-012).
`apps/web/app/lib/wire.server.ts` builds a third chain
(`buildStagedGenerationFallbackChain`) with different models (`gpt-4o` vs
`gpt-4o-mini`) (HEX-020). TUI hard-codes `https://api.openai.com/v1`
again (HEX-017).

**Options.**

1. **One infrastructure catalog** owned by `llm-driver` or `local-llm`
   infrastructure, injected as a port. Domain keeps only provider/model ids.
2. **Keep catalogs in domain** as “configuration as data” and document an
   exception in layer-rules.yaml.
3. **Per-app chains** (web vs TUI vs MCP) but one *builder* in a single
   package, not three literals.

**Recommendation.** (1) + (3): domain ids, one config adapter, per-app
composition of the chain. Delete the domain `createDefaultFallbackChain`
once wire.* and TUI consume the adapter.

**Consequences.** Prompt/stage temperature changes stop requiring domain
edits. Secret-name changes stay next to the vault adapter (HEX-008).

**Affected findings.** HEX-012, HEX-020, HEX-017, HEX-008.

## ADR-C6 — TypeScript workspace pin vs package-local 6.0.3

**Context.** Root `package.json` declares `typescript: ^5.4.5` (installed
5.9.3). `@hexagen/agentic-interaction` declares `typescript: ^6.0.3`
(MOD-001) plus Jest leftovers (MOD-003). The toolchain floor passed to
reviewers is TS 5.4 declared / 5.9.3 installed.

**Options.**

1. **Delete the local pin.** All packages typecheck with workspace 5.9.3.
2. **Raise the monorepo to TypeScript 6** (requires raising the declared
   root version, eslint parser verification, and a CI matrix bump).
3. **Keep both** (status quo) — rejected: two compilers, two truths.

**Recommendation.** (1) now. (2) only as a separate, scheduled upgrade
with `requires_toolchain_raise: typescript ^5.4.5 → ^6`.

**Consequences.** Option 1 may surface type errors currently hidden by
TS 6. That is the point.

**Affected findings.** MOD-001, MOD-003, MOD-006.

## ADR-C7 — Published `engines.node`: `>=20` vs `>=22.7.0`

**Context.** Root and CI are Node `>=22.7.0` / `22.7` / `22.12.0`.
`@hexagen/sync` and `@hexagen/arch-linter` publish `engines.node: >=20`
(MOD-004). ADR-0036 already assumes Node 22 webstorage behaviour.

**Options.**

1. **Align published engines with `>=22.7.0`.** Honest contract.
2. **Support Node 20** and add a CI job on 20.x that builds+tests the
   published CLIs.
3. **Leave the lie** — rejected.

**Recommendation.** (1) unless there is a documented customer on Node 20,
in which case (2).

**Consequences.** npm will warn (not necessarily fail) on Node 20 installs
of the published CLIs.

**Affected findings.** MOD-004, MOD-005.

## ADR-C8 — Where generated customer errors live

**Context.** Adobe/LLM templates emit

```ts
import type { FireflyError } from "../../../infrastructure/adobe/errors/firefly-errors";
```

from `src/domain/ports/out/*.port.ts`, with a comment calling this
“deliberate decoupling” (HEX-001). Type-only does not invert the
dependency. The same pattern is about to be copied for
`AgentRuntimePort` living *in* infrastructure (HEX-036).

**Options.**

1. **Domain-owned error unions** (`CreativeProductionError`) mapped at the
   adapter. Ports never import `infrastructure/`.
2. **Keep infra errors** and document a generator exception (status quo,
   rejected by layer-rules).
3. **Shared `Result` error codes** in the customer `shared/` kernel.

**Recommendation.** (1). The comment in the template is the bug.

**Consequences.** Every Adobe/LLM template port + the generated bundle
must change together (`yarn workspace web gen:template-questions` / bundle
regen).

**Affected findings.** HEX-001, HEX-036.
