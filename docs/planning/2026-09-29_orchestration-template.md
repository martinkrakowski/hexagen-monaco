## 0. What this plan answers

campaign-foundry built a working delegated-pipeline orchestrator — a skill, a gate with a repo-local
lock, a merge sweep, mutation-replay tooling, a wave-status server — one project at a time, under
real wave pressure. None of it exists in hexagen. Every project hexagen generates that wants the same
capability rebuilds it from nothing, the way campaign-foundry did, the way findings-store.md's own
§8 records hexagen-monaco itself doing for a first, unversioned, untracked copy on 2026-09-08. This
plan ports it once, as a template plus one published package, so `hexagen add orchestration` is the
whole story for every future project and `hexagen` — not each downstream repo — keeps it current.

### 0.3 D-id collision check

Run before writing this file existed (so it cannot self-match), per the Fable review's C2:

```
$ grep -rniw 'OW-D\|OW[0-9]' docs/planning
(no output, exit 1)
```

Zero hits — and this result is **sound**, not a lucky escape from a grep bug: `grep -w` requires a
non-word boundary only at the two _ends_ of the whole match, and `OW[0-9]` includes the digit inside
the pattern, so a real `OW1` (flanked by non-word characters, e.g. `**OW1**` or a space) would match
fine under `-w` — confirmed by running the identical shape against a **known positive**:

```
$ grep -rniw 'G-D[0-9]' docs/planning | head -3
docs/planning/gates-for-generated-projects.md:46:| **G-D0** | ...
docs/planning/gates-for-generated-projects.md:47:| **G-D1** | ...
docs/planning/gates-for-generated-projects.md:48:| **G-D2** | ...
```

Three real hits — `-w` with a digit class inside the pattern works. The genuine flaw is narrower than
"can never match either pattern": it is specifically the **bare `OW-D` alternative with no digit**,
which cannot match an id like `OW-D1` under `-w`, because `-w` needs a non-word character immediately
after the match and `D`/`1` are both word characters — there is no boundary between them. Demonstrated
directly, again against the same known-positive file (excluding this plan's own file, so the check is
against pre-existing content only):

```
$ grep -rniw 'G-D' docs/planning --exclude=2026-09-29_orchestration-template.md
(no output, exit 1 — despite G-D0/G-D1/G-D2 genuinely existing in gates-for-generated-projects.md:46-48)
```

Zero hits on a file that has three real matches for the _anchored_ form — the boundary bug is real, it
is just narrower than first stated. The corrected, digit-agnostic form:

```
$ grep -rniE 'OW-?D?[0-9]' docs/planning
(no output, exit 1)
```

All three runs (prescribed, corrected, and both controls) are clean against `docs/planning/` as it
stood before this file was written. `OW` and `OW-D` are unused. **Lane and decision ids in this plan
are `OW1`–`OW9` and `OW-D1`–`OW-D14`.**

## 8. Risks and what this plan does not pretend

- **The scrub lane's coverage-check test (OW1) is itself new machinery, unproven.** It is the single biggest risk to §0.2 requirement 1 actually holding — if it has false negatives (an orphaned rule it doesn't flag), campaign-foundry's context silently thins on port day. - **This plan does not fix campaign-foundry's own `gate.sh:5-6` unenforced "mirrors ci.yml" claim in campaign-foundry itself** — OW-D4's fix (one source of truth via `config.yaml` and a single gate-bin-invoking CI step) is a hexagen-side design decision; campaign-foundry keeps its own 19-step CI restatement (17 named, 2 unnamed `uses:`) until it independently adopts the published package (OW-D9's same boundary).
- **It does not build `quality-gate`/G2** — `format:check`/coverage remain a soft, conditional-no-op dependency (matching `check:env`) until `gates-for-generated-projects.md`'s own plan ships.
- **(Revised, §12 A-6 — no longer a blocker.)** r3's text follows for the record. **OW3 was blocked on two open campaign-foundry PRs merging (F-1, OW-D9)** — #631 (HX3b) and #630 (HX4), both `OPEN` as of this plan's writing.
