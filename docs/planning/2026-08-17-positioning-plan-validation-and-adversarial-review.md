## 1. Verdict in one paragraph

The plan's **strategic thesis survives review** — conformance-over-generation is the right repositioning, and the Gauntlet-infrastructure argument holds. But the plan is **factually wrong in both directions about the codebase**, and one of its two load-bearing execution assumptions is impossible as written. It _understates_ the conformance assets (the "Layer 2/3 conformance engine to build" already exists, is published to npm, and includes the baseline ratchet the plan calls adoption-critical), _overstates_ the platform gap in places (auth partially exists; client storage is schema-versioned and clobber-hardened), and — most importantly — its **"OSS CLI free forever" distribution wedge contradicts the repository's license**, which is source-available proprietary with commercial use prohibited, and whose README _already sells_ the not-yet-existent "automated brownfield ingestion engine" as a commercial offering. The plan therefore doesn't need a rewrite of its thesis; it needs a licensing decision, a truthful asset inventory, and a cheaper Phase 0.

## 3. Adversarial analysis — ranked findings

**A1. The distribution strategy is illegal under the product's own license. (Blocking.)**
The plan's wedge is "open-source CLI, free forever, npx, PR comments as marketing." The repo is licensed **Source-Available Evaluation** — read/run/evaluate only, _no commercial production use, no managed service, never transitions to open source_ — and the README already directs commercial licensing inquiries, including "access to the automated brownfield ingestion engine," to Krakowski Cloud Solutions, LLC. You cannot run a CodeRabbit-style bottom-up adoption motion with a license that forbids the adopters' use. Either (a) carve out and re-license the wedge subset (`arch-linter` + a report command) under Apache-2.0/MIT while keeping the platform proprietary — the standard open-core split — or (b) abandon bottom-up and sell top-down/through engagements, which changes §2.6 and §2.7 entirely. This is the first decision, before any code.

**A2. The README sells a product that does not exist.**
"Automated brownfield ingestion engine" is advertised as a commercial offering; verification found zero inference code and a `coming-soon` redirect stub. Anyone doing diligence — a prospective client, a partner, an acquirer — will find this gap in an afternoon. Either build the honest v1 (runbook Phase 0) or soften the README line now. Marketing ahead of the artifact is precisely the first-run-trust failure the plan itself calls existential (§7.1).

**A3. The conformance engine is layout-coupled, which quietly breaks the FDE story.**
"`hexagen-lint` runs against any repo with a manifest" is true only if the repo is laid out Hexagen-style (`<workspacesDir>/<ctx>/`, Hexagen layer conventions; `layer-classifier.ts` is regex-over-generated-paths). A real client repo on day 1 of an engagement will not match, so the flagship "day-one drift report" fails at `FATAL ERROR: Could not find project root`. The cheapest unlock in the whole plan is **a layout-mapping config** (map client directories → contexts/layers) so the existing linter runs on foreign repos — weeks, not months, and it converts the already-built engine into the FDE tool. This should displace "build inference" as Phase 0's core.

**A4. Phase 0 as written is mis-scoped in both directions.**
It budgets 2–4 weeks to build inference (too little for first-run-safe inference on arbitrary repos — the thing §7.1 says you get one shot at) while ignoring that the validation question ("does the conformance verdict land with engineers who aren't you?") can be answered _without any inference_ via layout-mapping + a hand-bootstrapped manifest on 2–3 foreign repos. Cheaper experiment, same gate, no reputational exposure from a wrong inference.

**A5. "History is the moat" has no floor under it yet.**
The paid tier is hosted drift history, but the platform runs single-process better-sqlite3 with in-memory rate limiting, k8s manifests that contradict the storage assumption, and telemetry that evaporates at container log rotation. None of this is surprising pre-revenue, but the plan's §3.6 estimates should absorb the corrections in §2.3 — some items are cheaper (auth), one is harder than listed (choosing a DB story that survives >1 replica _before_ tenancy).

**A6. Two honesty liabilities inside the product would surface in a paid engagement.**
(1) The import round-trip is mitigated-by-bypass, not lossless — an FDE workflow that leans on import→edit→export will hit it. (2) MCP mutation tools bypass the approval path — the "agents constrained by the manifest" pitch is undermined if the agent-facing tools can silently rewrite the manifest itself. Both are fixable; both should be fixed before they're demo'd.

**A7. The quota contract violation (see §2.3) is small but corrosive.**
A conformance product's brand is "we catch contract drift" — while its own codebase has a documented internal contract ("call ONLY on the unauthenticated path") violated by six routes. Fix it and use it: it's a perfect dogfooding anecdote for the marketing narrative.

**What survives adversarial review intact:** the repositioning thesis (§1), the anti-ICP discipline (§2.2), the manifest-as-Gauntlet-bar argument (§4.2) — which verification _strengthened_: the drift score, ratchet, and bounded-context decomposition primitives all actually exist in the tree today — and the phase-gate/kill-criterion structure (§6), which this review re-scopes but keeps.

## 4. FDE go-to-market: the "Swiss-army-knife" feature set, grounded

The honest insight from verification: **the FDE kit is mostly assembled, mis-packaged, and blocked by exactly two things — layout coupling (A3) and licensing (A1).** The plan imagined building a product; the tree says you're mostly productizing one.

### 4.1 What an FDE can already do today (package this, don't rebuild it)

| Capability                                                | Existing artifact                                                                                  |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Declare a client's architecture as an executable contract | Manifest schema + `.architecture/` split files + invariants YAML                                   |
| Gate PRs on drift                                         | `hexagen sync --check` + `hexagen-lint` + ratchet baseline + auto-injected CI workflow             |
| Land in a messy repo without 4,000-violation dumps        | `arch-lint-baseline.json` ratchet (already dogfooded)                                              |
| Show architecture change as a reviewable event            | `hexagen arch diff` / MCP `hexagen_diff_manifest`                                                  |
| Constrain coding agents to declared boundaries            | MCP server: 19 tools incl. `hexagen_audit_boundaries`, dependency graph, invariants resources      |
| Safe automated refactors                                  | `hexagen arch refactor` gated by validation suite (build+typecheck+lint+tests, backup/auto-commit) |
| Live violation monitoring during a working session        | TUI boundary-violation inspector                                                                   |
| Client-controlled LLM keys                                | Deployed BYOK (AES-256-GCM, durable revocation)                                                    |

### 4.2 The gap between that and a Swiss-army-knife — build in this order

1. **`hexagen adopt` — layout-mapping config (the unlock).** A `.architecture/layout.yaml` that maps existing client directories to contexts/layers so `hexagen-lint`, ratchet, and `arch diff` run on non-Hexagen repos. Kills A3. Without it, every other FDE feature is greenfield-only.
2. **`hexagen bootstrap` — assisted manifest creation, not inference.** Interactive: read workspaces + import graph (reuse `port-analyzer` ts-morph infra), propose candidate contexts _as questions_, human ratifies, emit manifest + baseline. Ships the "day-one architecture map" deliverable honestly. Full LLM inference becomes a later upgrade to this command, developed against a ground-truth corpus (Gauntlet subject, plan §4.1) — never the first-run path.
3. **`hexagen report` — the engagement artifact.** One command → self-contained HTML/Markdown: context map (Mermaid — renderer already exists in the accept view), drift summary, baseline count, ratchet trend. This is the week-one credibility deliverable and the handoff document. Cheap: it's a formatter over outputs that already exist.
4. **CI action + PR comment.** Wrap `sync --check` + `hexagen-lint --ratchet` in a published GitHub Action that comments only _this PR's_ new violations. The distribution surface — gated on the A1 licensing decision.
5. **Engagement handoff pack.** `report` + manifest + baseline + suppressions-with-expiry, zipped. "Documentation that can't go stale" made literal.
6. **Agent constraint hardening.** Route MCP mutation tools through the approval path (A6); add a pre-commit `audit-boundaries` hook; document the "pin your agent to one context" workflow. This is the pitch competitors can't copy from a linter.
7. **Gauntlet-guided remediation** (plan §4.3) as a billable service offering first, product later — drift score from X to Y is the invoice line.

### 4.3 What to cut or defer from the original feature list

- **Full autonomous inference on stranger repos** — deferred behind the bootstrap command + corpus; the one-shot-trust risk (§7.1) is too high to lead with.
- **Cross-repo contract conformance** — nothing exists; defer until a platform customer asks with money.
- **Semantic drift Tier 2** — real differentiator, but each check needs a measured false-positive budget; ship off-by-default after the wedge is landing.
- **Blame attribution, hosted dashboards, drift-score trend UI** — Phase 2, after the licensing decision proves a bottom-up funnel is even possible.
