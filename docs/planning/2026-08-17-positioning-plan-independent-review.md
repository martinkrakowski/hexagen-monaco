## 1. Overall verdict

**Safe to execute with amendments — but two of the runbook's concrete work items are wrong as written and one estimate class is systematically understated.** The strategic core survives independent attack: conformance-over-generation is the right repositioning, the asset inventory in the review is broadly accurate (engine shipped and published, inference genuinely absent, layout coupling real), and the phase-gate structure is sound. However: (a) the runbook's Phase 0.4 "quota contract violation" fix contradicts a **recorded, dated product decision** the review failed to find — half of that "live defect" is an accepted tradeoff, and one of its six cited routes actually honors the contract; (b) the layout-coupling problem is **worse** than the review states — on a typical foreign repo the linter either crashes on an unguarded `tsconfig.base.json` read or, worse, **prints "Architecture is compliant" after silently scanning zero files** — which materially raises the Phase 0.1 estimate and adds a mandatory fix the runbook doesn't list; (c) the ratchet is a whole-repo identity baseline, not per-PR gating, so the Phase 1.2 CI action's "diff against base-branch baseline" is new engineering the estimate doesn't absorb; and (d) the licensing constraint is **softer** than all three documents claim — "never transitions to open source" exists only in the README, not in the LICENSE, and the sole-copyright-holder position makes relicensing frictionless. The amendments in §5 are the minimal set before Phase −1 decisions.

## 3. New findings (ranked)

**N1 — The linter's foreign-repo failure mode is a silent false green, not a crash. (Severity: high — trust-critical for the FDE story.)**
`cli.ts:365-367` silently `return`s for any manifest context whose directory doesn't exist on disk; a run that matched _nothing_ then prints "Architecture is compliant" (`cli.ts:735-737`) and exits 0. An FDE on day one of an engagement gets a green report over zero scanned files — precisely the first-run trust catastrophe plan §7.1 calls existential, in the _opposite_ direction from the one the documents worry about. Amends: review A3, runbook 0.1. **The Phase 0.1 definition of done must add: the run fails loudly (exit 2) when zero contexts resolve, and the report states how many files were scanned.**

**N2 — Runbook Phase 0.4's quota fix contradicts a recorded decision. (Severity: high — the runbook instructs undoing settled product state.)**
Evidence in claim 5. The double-charge was flagged at implementation (PR #337), decided as D2 (2026-07-25), and closed "leave as-is" on 2026-08-13 with a documented rationale (superseded by the planned subscription gate). The review presented it as a newly found "live defect" and the runbook scheduled its removal. Rewrite the row to the defensible residue: **add the signed-in bypass to the 5 generate routes** (this _is_ a real divergence from PR #337's stated contract), drop the extract-decisions citation (it honors the contract), drop "BYOK users are metered" (no BYOK path exists in generation), and either keep the double-charge or explicitly reopen D2 — silently reversing it is the exact "contract drift" failure the product claims to catch.

**N3 — The ratchet is not per-PR gating, and the CI action's headline behavior is unbuilt. (Severity: high — invalidates a Phase 1 estimate.)**
The ratchet suppresses by violation identity over a whole-repo scan; baseline growth and staleness are review-enforced, not machine-enforced (`lint.yml:167-172` states this outright). Runbook 1.2 promises "comments **only violations introduced by this PR** (diff against base-branch baseline)" — that requires computing a base-branch baseline per PR (checkout/cache of base, or carrying baselines in the action), handling renamed files (identity key breaks on rename), and machine-enforcing growth for the first time. Real work; the 1–2 week estimate assumed it existed. Also amend plan §3.4's row ("enforce only on changed code" → "suppress known violations by identity; changed-code gating is Phase 1 work").

**N4 — "Never transitions to open source" is a README sentence, not a license term. (Severity: medium — materially changes D-1's option space.)**
`README.md:381` asserts it; the LICENSE (read in full, 33 lines) contains nothing of the kind. Krakowski Cloud Solutions, LLC is sole copyright holder (`LICENSE:3-4,26`) with no external contributors to clear, so relicensing any subset is a decision, not a negotiation. All three documents treat the license posture as a heavier constraint than it is. Consequences: (a) D-1 has more options than "Apache-2.0 open-core vs stay proprietary" — see §7; (b) legal hygiene: the README currently _overpromises restriction_ beyond the license text — rewrite the license section whichever way D-1 goes.

**N5 — Unguarded `tsconfig.base.json` requirement crashes on typical foreign repos. (Severity: medium.)**
`cli.ts:144` + `:304-306`: no flag, no `existsSync` guard, no try/catch. A repo whose root config is `tsconfig.json` (the default) dies with a raw ts-morph stack trace and Node's generic exit 1 — indistinguishable from "violations found," violating the linter's own 0/1/2 exit-code contract (`cli.ts:53-69`). Must be on the Phase 0.1 touch-point list; it isn't.

**N6 — Version drift: the registry's latest release is v0.9.0; the tree is 0.10.0, an untagged breaking minor. (Severity: medium.)** _(Corrected in adjudication — the original wording here claimed "the arc documents cite 0.9.0"; none of docs 1–3 does. The real fact stands as restated.)_
All publishable manifests read `0.10.0`, but `git tag` shows `v0.9.0` as the newest release tag — 0.10.0 has never been published. `CHANGELOG.md:8-10,42` marks it deliberately breaking ("A project that passed the linter on 0.9.x can therefore fail on 0.10.0"). Any CI action, README quickstart, or engagement kit must decide whether it targets the last published tarball or the next release, and pin it; the review's "published to npm" evidence silently describes 0.9.0.

**N7 — The commercial funnel has no endpoint. (Severity: medium for GTM, trivial to fix.)**
`README.md:383` solicits commercial licensing inquiries — with no email, no URL, no form; the only link in the section is `./LICENSE`. Every marketing motion in §6 currently terminates in a dead end. One-line fix, same day as D-2.

**N8 — No ADR records the licensing posture. (Severity: low-medium.)**
61 ADR files cover far smaller decisions; the single most consequential commercial decision is undocumented. Whatever D-1 decides should land as an ADR (with the D2-quota episode in N2 as the cautionary tale for why decisions must be findable — the author's own review failed to find D2 because it lived in a planning doc, not an ADR).

**N9 — Stale operational metadata around the ratchet. (Severity: low.)**
`lint.yml:155` (line corrected in adjudication) says "the 34 accepted entries"; the baseline holds 4. The 4th entry carries an informal prose `note` field that survives only because `parseBaseline` ignores unknown fields (`ratchet-baseline.ts:124-134`). Cheap cleanups that matter once the ratchet format becomes a public product surface (runbook 1.3 extends it with `reason`/`expires` — formalize the schema then).

### Part 2 attack — strategy-level findings

**Competitive field (the review's blind spot is real but survivable).** The documents name only dependency-cruiser and eslint boundary plugins. The actual field: [Nx module boundaries](https://www.stefanos-lignos.dev/posts/nx-module-boundaries) (tag-based dependency rules, mature, free, already inside many TS monorepos), Sheriff, dependency-cruiser-as-policy-engine, ts-arch/ArchUnit-style test assertions, and CodeScene on the behavioral side. Structural checking (Tier 1) is fully commoditized — the plan already concedes this. The strongest competitor is the one the review prompt predicted: **harness vendors shipping native constraint layers.** This is no longer hypothetical — 2026 research literature includes deterministic control planes for LLM coding agents and OS-level policy enforcement for agent harnesses (e.g. [A Deterministic Control Plane for LLM Coding Agents](https://arxiv.org/pdf/2606.26924), [ActPlane](https://arxiv.org/pdf/2606.25189)), and the guardrails conversation has moved from prompts to architecture-level enforcement ([Checkmarx](https://checkmarx.com/blog/guardrails-for-agentic-development/)). The differentiation that survives this: harness-native guardrails will be _harness-scoped and session-scoped_; the manifest is _repo-scoped, versioned, human-ratified state_ that outlives any one harness and feeds all of them (MCP already demonstrates this). That is the plan's §7.5 hedge, and it holds — **but only if the history layer actually exists**, which circles back to A5: today the telemetry is discarded and nothing is server-authoritative. The moat argument is currently a promissory note; Phase 2 is what makes it true.

**The FDE thesis and its falsifier.** The Phase 0 gate (3-of-5 engineers agree the contexts are right) measures _correctness agreement_, which is vulnerable to politeness. Add a costly-signal clause: the gate counts only engineers who take an artifact-generating action unprompted — asks to run it on another repo, asks for the manifest file, or lets you open a PR adding the check to their CI. Agreement plus zero pull = fail. This costs nothing and converts the gate from an opinion survey into a demand probe.

**Phase-gate integrity.** Phases 0, 2, 3, 4 have measurable, kill-capable gates. Phase 1's gate contains an escape hatch: "at least two external parties running it in CI unprompted **or** one engagement where the day-one report visibly changed the client conversation" — the second clause is self-judged and satisfiable by charitable interpretation of any engagement. Tighten: the engagement clause counts only if the client asks to keep the tooling (pays for it, or requests the handoff pack) after the engagement ends.

**Effort realism.** The repo demonstrably imposes: contract tests against built dist (5 of 6 contract suites spawn a physically-copied `dist/cli.js`), co-versioned two-package publishing with a staging script, 68 test files in sync alone, and a first-run-green capstone CI. Estimates that must absorb this overhead: 0.1 (adopt — plus N1/N5 fixes), 1.2 (CI action — plus N3), 1.3 (suppressions — the baseline format is consumed by `parseBaseline`, the lint workflow, and the published-consumer contract layout; a format change touches all three). A uniform +50% on Phase 0–1 engineering rows is the honest correction.

**Most important omission across all three documents:** the **security/NDA posture of running the tool inside client repositories** — the FDE motion's core act. What the documents never state: which components phone home (the linter is deterministic and local — a genuine selling point nobody wrote down), what the LLM-touching paths send where (cloud generation goes through OpenRouter; BYOK exists but only on chat), and what an engagement-mode "nothing leaves the machine" guarantee looks like. For a consultant under NDA this is the first question in procurement, and it has a _good_ answer today (the deterministic local CLI; BYOK is a server-side proxy per ADR-0030 and belongs in the "named LLM paths" column, not the air-gap claim) that the marketing never makes. Second-tier omissions, confirmed absent: consulting-path pricing (never priced in any document), the migration story for existing generator users, and the support burden of a public wedge (issues/PRs against a solo maintainer — the fair-source recommendation in §7 partially mitigates by keeping the surface small).

## 7. Licensing strategy for a paid product

**Premise (per the owner's directive): this is a paid product.** That rules out the runbook's Option A as written — permanently Apache-2.0-ing the engine gives the core asset away and lets any harness vendor absorb it (§4's strongest competitor) — and it makes Option B's cost explicit: no bottom-up funnel at all. The false dichotomy resolves in the middle, which the fair-source family was built for.

### 7.1 Recommended structure — three layers

| Layer                                                | Components                                                                                                           | License                                                                                                                           | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Wedge (free to use, source-available, protected)** | `tools/arch-linter`, future `adopt`/`bootstrap`/`report` commands, the CI action                                     | **FSL-1.1-Apache-2.0** ([Functional Source License](https://fsl.software/))                                                       | Free for _any_ use — including commercial internal use, which is what a funnel needs and what the current evaluation license forbids — with a single carve-out: no competing product/service. Each release auto-converts to Apache-2.0 after 2 years, which answers "will this get rug-pulled" for adopters without giving competitors the current engine. Proven shape ([Sentry's reasoning](https://blog.sentry.io/introducing-the-functional-source-license-freedom-without-free-riding/), [TechCrunch](https://techcrunch.com/2023/11/20/with-functional-source-license-sentry-wants-to-grant-developers-freedom-without-harmful-free-riding/)). |
| **Platform (paid)**                                  | Web app, staged generation pipeline, hosted history/dashboards, multi-repo, agent-constraint pack, `packages/sync`\* | **Proprietary commercial** (current license, cleaned up) — or **[FCL](https://fcl.dev/)** if a self-hosted paid tier is ever sold | This is the product. History, dashboards, and the agent pack are where §2.6's moat lives; nothing here needs public licensing to sell. FCL (FSL + ELv2-style limits) becomes relevant only if enterprise self-hosting (plan §3.7) is offered — it permits paid self-hosting while forbidding resale.                                                                                                                                                                                                                                                                                                                                                 |
| **Free tier of the paid platform**                   | Hosted product, quota-limited                                                                                        | Terms of service, not a code license                                                                                              | Already built (durable quota store). The planned GitHub-login subscription gate is the paid boundary — consistent with decision D2, which N2 preserves.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

\* `packages/sync` placement is a judgment call: it is co-published with the linter today, but it contains the generator/scaffolding value. Recommendation: keep sync under FSL _if_ the wedge story needs `sync --check` in the CI action (it does, per runbook 1.2); the 2-year-old converted version of a fast-moving tool is not a competitive threat, and splitting the co-versioned pair onto two licenses complicates the publish pipeline for little protection.

### 7.2 Why this beats both runbook options

- **vs. Option A (Apache-2.0 open-core):** FSL preserves the paid product's defensibility — nobody can ship "HexagenLint Cloud" or fold the current engine into a competing harness — while losing almost none of the adoption surface (the users Apache attracts that FSL doesn't are competitors and license-purists; the funnel targets neither). The DOSP conversion keeps the OSS-credibility signal that pure proprietary lacks.
- **vs. Option B (fully proprietary):** the current license _prohibits the customer's own evaluation from touching production_, which forecloses even the consulting-adjacent motion ("run it in your CI during the engagement" is a commercial production use). Option B doesn't just shrink the funnel — as written, the license undermines the _paid_ engagement workflow too.
- **N4 makes this cheap:** sole copyright holder, no CLA debt, no contributor negotiations. The "never open source" sentence was only ever in the README.

### 7.3 Execution checklist (folds into Phase −1 / D-1)

1. Add per-package `LICENSE` files (FSL text in `tools/arch-linter/`, and `packages/sync/` if included) — today the staging script falls back to the root evaluation license and ships it in every tarball (`prepare-publish-package.js:217-225`); after the split, the root fallback becomes a bug. Update `license` fields (keep `"SEE LICENSE IN LICENSE"` or use the `FSL-1.1-Apache-2.0` identifier as Sentry does; there is no bare SPDX short-form guarantee — the file is authoritative).
2. Rewrite `README.md:373-385`: per-package license statements; keep the platform proprietary language scoped to the platform; delete or scope line 381; add the contact endpoint (N7).
3. Update both package READMEs (`packages/sync/README.md:227`, `tools/arch-linter/README.md:183`) — they currently restate the evaluation terms and will ship inside the next tarballs.
4. **Record as an ADR** (N8): the layer table above, the FCL trigger condition, and the rule that new packages default to proprietary unless deliberately placed in the wedge.
5. Note the version boundary: already-published tarballs (≤0.9.0, the last published release — 0.10.0 is untagged/unpublished, see N6) remain under the evaluation license forever; the relicense applies from the next release actually published. State this in the CHANGELOG entry.
6. Trademark stays out of the code license: "Hexagen-Monaco" the mark is protected independently of what the FSL grants — one sentence in the README's trademark line.
7. If external contributions are ever accepted on FSL packages, add a DCO or lightweight CLA _first_ — sole-ownership is what makes future license moves free, and it is worth protecting.

### 7.4 Pricing shape (adjusted to the licensing structure)

The plan's repo-based pricing survives. The tier boundary moves slightly: everything deterministic and local is free (FSL wedge — linter, adopt, bootstrap, report, local baseline); everything **stateful or cross-cutting** is paid (hosted history and trends, multi-repo dashboards, org policy, the agent-constraint pack as a supported/integrated product, engagement tooling). Consulting engagements — never priced in any of the three documents — should be priced as: diagnostic (fixed-fee day-one report), remediation (Gauntlet-guided, "drift score X→Y" as the invoice line per runbook Phase 3), and retainer (the CI gate + quarterly re-ratification). The diagnostic is deliberately cheap; it is the funnel's paid top for clients who won't self-serve.

## 8. Adjudication addendum (2026-08-17, second review round)

Four further reviewer passes were run against this review (two deep, one concurring, one that applied edits to the runbook directly). Every contested claim was re-verified against the tree before ruling. The runbook now reflects all rulings; this addendum records what changed **in this review's own conclusions**.

**Overturned:**

- **Amendment 1 (the signed-in bypass) is withdrawn.** This review correctly narrowed the "quota defect" but then prescribed the wrong remedy: GitHub OAuth in this codebase is publish-authorization, not entitlement (no accounts table, no subscription, no billing), so an unconditional bypass on the five generate routes — the expensive, server-paid path — would hand unmetered cloud generation to anyone who OAuths, before billing exists. The chat-vs-generate inconsistency is real but resolves conservatively under quota-D2: keep metering generate until the subscription gate ships; treat the `enforce-quota.ts:35` comment as stale relative to that decision. The inconsistency is now recorded as a product question inside the future quota-D2 ADR. Phase 0 ships **no** quota code changes.
- **A6 part 2 upgraded UNVERIFIED → CONFIRMED** (evidence in the amended §4 table row). Part 1 (import round-trip) remains unaudited.

**Corrected (factual):** N6's "the arc documents cite 0.9.0" (they don't; the real drift is registry `v0.9.0` vs untagged 0.10.0 tree); N9's line number (`lint.yml:155`); "59 ADRs" (61 files, duplicate 0009/0010); §6's bundling of BYOK into the "nothing leaves the machine" claim (BYOK is a server-side proxy, ADR-0030); and one nuance on N1 — a typical foreign repo _fatals_ on first contact (missing manifest); the false green appears on the first run **after** adopt/bootstrap writes a manifest, which is the run the FDE trusts, so severity stands.

**Refined:** vacuity for the 0.1 loud-failure DoD is "zero resolvable files scanned," not "any missing context dir is fatal" (Hexagen repos legitimately declare contexts before scaffolding them); `getLayerAllowedImports` is already config-driven — only the purity-check dispatch is hardcoded, so 0.1 must not rebuild it; N3's scope is "identity-key rename resilience + base-branch baseline CI orchestration," not a ratchet redesign (estimate correction stands); the Phase 0 costly-signal gate now ranks usage-signals (engineer volunteers the output into their own artifact) above permission-signals (lets you open a CI PR); the §7.2 argument that the evaluation license forecloses even engagement CI use is promoted to the lead argument for relicensing; the competitive-threat claim is time-bounded (no shipping harness enforces repo-scoped ratified manifests as of 2026-08; the cited papers are direction, not product).

**Added (new decisions, now in the runbook):** **D-0** — capacity: the remediation arc (Phases 6–8 in flight on this same branch) and positioning Phase 0 cannot both run full-speed solo; one calendar, decided first. **D-3 before D-1** — FSL is the _business_ answer; proprietary-plus-engagement-grant is a coherent _consulting_ answer this review under-steelmanned. **ADR-ification as the Phase −1 exit criterion** — D-0/D-3/D-1/D-2/quota-D2/D-4 each land in `.architecture/decisions/` before Phase 0 code; the quota-D2 near-miss is the proof this matters. **D-4 promoted to same-day** for the k8s manifests (applying them as written doubles free-tier quotas per-pod and silently un-revokes BYOK keys). **The sync sub-decision** — FSL the whole generator vs extract the `--check` surface — must precede the per-package LICENSE files.

**Rejected from the other reviewers:** the "FSL rider / perpetual internal-use grant" appendix one pass added to the runbook — removed. FSL-1.1's grant is already perpetual per-release for non-competing use; a bespoke rider on a standard license increases the legal-review friction it purported to solve, and its carve-outs muddied the Apache conversion. Enterprise-specific certainty belongs in that customer's commercial agreement.
