# Managed Production `docker-compose.yml`

**Status:** Plan
**Suggested branch:** `feature/managed-deploy-compose`

> Bring the production Docker Compose definition into version control and have
> `deploy.yml` ship it to the VPS, so the container's runtime wiring (env
> injection, ports, restart policy, reverse-proxy hookup) is reproducible and
> reviewable instead of living only on the server.

---

## TL;DR — problem & fix

The production `docker-compose.yml` lives **only on the VPS** at
`/opt/hexagen-monaco/docker-compose.yml`; it is not in the repo. The deploy
writes `/opt/hexagen-monaco/.env` and runs `docker compose down && up -d` against
whatever compose file happens to be there.

Two consequences:

1. **Drift / invisibility.** The single most important runtime contract (which
   env vars reach the container, ports, the reverse-proxy network) is
   unversioned, unreviewable, and undocumented.
2. **The live sign-in bug.** Production `/api/auth/providers` still reports
   `http://localhost:3000` after a successful deploy — `NEXTAUTH_URL` is written
   to `.env` but never injected into the container. A project-level `.env` is
   auto-loaded for `${VAR}` **interpolation in the compose file**, but it only
   becomes **container environment** when the service declares `env_file: .env`
   (or an explicit `environment:` block). The current VPS compose evidently does
   neither for the new vars.

This plan vendors the compose into the repo, adds `env_file: .env` to the web
service (the actual fix), and makes the deploy ship the file.

> **Immediate unblock (independent of this plan):** add `env_file: [.env]` to the
> web service in the VPS compose and `docker compose up -d`. That fixes sign-in
> now; this plan makes it durable and version-controlled.

---

## Goal

1. A reviewed `docker-compose` for production lives in the repo and is the source
   of truth.
2. The deploy ships it to the VPS and uses it (no hand-edited server file).
3. The web service loads `.env` via `env_file:`, so **all** runtime vars
   (`NEXTAUTH_URL`, `NEXTAUTH_SECRET`, `GITHUB_ID`, `GITHUB_SECRET`, `LLM_*`,
   `AUTH_SECRET`) reach the container.
4. The existing reverse proxy / TLS for `app.hexagen-monaco.cloud` is preserved
   exactly — no TLS or routing regression.
5. Secrets stay out of the repo: `.env` remains generated by the workflow and
   git-ignored.

## ⚠️ Blocking prerequisite — capture the current VPS compose

We cannot author a faithful repo compose without the current one. **Before Phase
1**, capture it verbatim:

```bash
cat /opt/hexagen-monaco/docker-compose.yml
docker compose -f /opt/hexagen-monaco/docker-compose.yml config   # fully resolved
docker compose ps                                                  # service names
docker network ls                                                  # proxy network?
```

The critical question this answers: **is the reverse proxy in the same compose
project as the web service, or separate?** That decision shapes the whole
approach (see Risks).

## Architecture / approach

- **Location:** `deploy/docker-compose.prod.yml` (new `deploy/` dir; keeps infra
  artifacts together and out of the app build context).
- **Faithful copy first, one change second.** The repo file must reproduce the
  captured VPS compose _exactly_ (image name, ports, networks, proxy labels,
  restart policy), then add the single behavioral fix: `env_file: [.env]` on the
  web service.
- **Image contract:** web service uses `image: hexagen-monaco-web:prod` with
  `pull_policy: never` and **no `build:`** — the image is `docker load`ed from the
  shipped tar, not built or pulled on the VPS.
- **Env contract:** `env_file: [.env]` (flow-sequence form — `env_file: - .env`
  on one line is **not** valid YAML; use `[.env]` or a newline block list). The
  workflow keeps writing `.env`; it stays git-ignored. Optionally vendor a
  `deploy/.env.example` documenting every expected key.
- **⚠️ `env_file` path resolution.** Compose resolves a relative `env_file`
  against the **compose file's directory**, so the shipped compose and the
  generated `.env` must end up in the **same** directory. The workflow writes
  `.env` at `/opt/hexagen-monaco/.env`, so the compose file must land at
  `/opt/hexagen-monaco/docker-compose.prod.yml` — **not** a `deploy/`
  subdirectory. `appleboy/scp-action` preserves the source path by default
  (`deploy/…` would land at `/opt/hexagen-monaco/deploy/…`, making `env_file`
  resolve to `…/deploy/.env` → the sign-in bug returns). Two fixes:
  - **Recommended (no action-specific behavior):** stage at the runner root first
    — `cp deploy/docker-compose.prod.yml docker-compose.prod.yml` — then SCP with
    `source: docker-compose.prod.yml`.
  - `appleboy/scp-action@v0.1.7` **does** support `strip_components`
    (confirmed against its inputs: "removes leading path elements when
    extracting"), so `source: deploy/docker-compose.prod.yml` +
    `strip_components: 1` also lands it at the root.

  Either way, run compose from `/opt/hexagen-monaco` so `.env` co-locates.

- **Deploy change:** SCP `deploy/docker-compose.prod.yml` so it lands at
  `/opt/hexagen-monaco/docker-compose.prod.yml` (root, see above), then run
  compose against it from `/opt/hexagen-monaco`.

### Data flow (after)

```text
deploy.yml: build image → save tar
            → SCP {hexagen-web.tar.gz, deploy/docker-compose.prod.yml} → VPS
            → SSH: write .env → docker load → docker compose -f … up -d → prune
container env := .env (via env_file) → NEXTAUTH_URL etc. resolved correctly
```

## Phases

**Phase 1 — Vendor the compose (no behavior change beyond the env fix)**

- Capture the VPS compose (prerequisite above) and commit a faithful copy as
  `deploy/docker-compose.prod.yml`.
- Add `env_file: [.env]` to the web service. Set `pull_policy: never`, an
  explicit `restart: unless-stopped`, and confirm the `3000`/proxy wiring matches
  the captured file byte-for-intent.
- Ensure `.env` is git-ignored; add `deploy/.env.example` (keys only, no values).
  It is **repo-only developer documentation** — never SCP'd to the VPS; the real
  `.env` is generated there by the workflow.
- _Exit:_ `docker compose -f deploy/docker-compose.prod.yml config` resolves; a
  diff against the captured VPS `config` output shows **only** the `env_file`
  addition.

**Phase 2 — Ship it from the deploy**

- Add an SCP step (or extend the existing one) to transfer the compose file so it
  lands at `/opt/hexagen-monaco/docker-compose.prod.yml` (root — stage at runner
  root or use `strip_components: 1`; see the path-resolution note above).
- **Make the SSH script fail loudly.** `appleboy/ssh-action` does **not** run with
  `set -e` by default, so a mid-script failure (e.g. a corrupt tar or full disk on
  `docker load`) silently continues — `up -d` then keeps the _old_ container
  running and the deploy reports success. Start the script with
  `set -euo pipefail`, and guard the load by comparing the image ID before/after
  (fail if `docker load` didn't move the `:prod` tag) so a bad image can't be
  masked by a "successful" deploy.
- **Reorder the SSH script for near-zero downtime** — drop `docker compose down`
  and the explicit `docker rmi`:
  1. `docker load < hexagen-web.tar.gz` — overwrites the `:prod` tag, leaving the
     old image dangling. _(With `set -e` + the ID guard above, a failed load
     aborts here instead of proceeding.)_
  2. `docker compose -f docker-compose.prod.yml up -d` (optionally `--no-deps web`)
     — Compose sees the new image ID and recreates only the web container in a
     fraction of a second, instead of a full stop/start cycle. Run from
     `/opt/hexagen-monaco` so `.env` resolves correctly.
  3. `docker system prune -a -f --volumes` — reaps the now-dangling old image.

  This also dovetails with the proxy risk: `up -d [--no-deps web]` never cycles a
  co-located proxy, whereas `down` would.

- Keep the `.env` heredoc.
- _Exit:_ a deploy succeeds; `curl https://app.hexagen-monaco.cloud/api/auth/providers`
  shows `app.hexagen-monaco.cloud` (not localhost); `docker compose exec <web>
printenv | grep NEXTAUTH_URL` is present; GitHub sign-in round-trips; no
  observable TLS/proxy downtime during the swap.

**Phase 3 — Hardening (optional)**

- `healthcheck:` on the web service (e.g. `GET /api/health` or `/`) so compose
  reports readiness.
- Tag images by git SHA (`hexagen-monaco-web:${GIT_SHA}`) **in addition to**
  `:prod`, enabling rollback. _Deliberately not Phase 1:_ rollback only works if
  the previous image is **retained**, which directly conflicts with the
  `docker system prune -a -f --volumes` that exists specifically to keep a ~7 GB
  VPS from OOMing on the next deploy. Doing this right means replacing the blanket
  prune with a "retain the last N tags" reaper (label-based exemptions) — a real
  change to the memory strategy, not a one-liner. Keep the live recreate on the
  stable `:prod` tag (so `up -d` detects the image-ID change); use the `:${SHA}`
  tag only as a retained rollback target. Sequence this _after_ the env fix is
  shipped and verified.
- If the proxy is co-located, split it into its own compose project so a web
  redeploy never cycles TLS (see Risks).
- Document the topology in `.github/workflows/README.md`.

## Risks & mitigations

- **Reverse proxy / TLS regression (highest risk).** If the proxy shares the
  compose project, `docker compose down` cycles it → brief TLS/routing outage,
  and a wrong repo file could break HTTPS entirely.
  - _Mitigation:_ capture first; reproduce proxy service/labels/network exactly.
    Prefer `docker compose up -d --no-deps web` (recreate only web) over a full
    `down`. Consider splitting the proxy into its own compose project so app
    deploys never touch it.
- **External network coupling.** The web service may attach to an external
  proxy network (e.g. `networks: [web]` with `external: true`). Omitting it
  drops the site off the proxy.
  - _Mitigation:_ carry the exact `networks:` block from the captured file.
- **Secret leakage.** Never commit `.env`. Keep it workflow-generated and
  git-ignored; `deploy/.env.example` holds keys only.
- **Image not built on VPS.** A stray `build:` or default `pull_policy` would
  make compose try to build/pull instead of using the loaded tar.
  - _Mitigation:_ `image: hexagen-monaco-web:prod` + `pull_policy: never`, no
    `build:`.
- **Prune timing.** `docker system prune -a -f --volumes` must stay _after_ `up
-d` and remains volume-safe only while the app is stateless (already
  documented).

## Open decisions

1. **Proxy ownership** — is the reverse proxy in the same compose project, a
   separate one, or host-level? (Answered by the capture step; drives Phase 3.)
2. **File name/location** — `deploy/docker-compose.prod.yml` vs root
   `docker-compose.prod.yml`. _Tradeoff:_ `deploy/` keeps infra grouped but needs
   the stage-at-root / `strip_components` step so the file lands beside `.env` on
   the VPS; root placement makes the SCP trivial but loses the grouping.
   (Recommend `deploy/` + stage-at-root.)
3. **Image tagging** — keep `:prod`, or move to `:${GIT_SHA}` for rollback (see
   Phase 3 for the prune conflict).

## Out of scope

- Moving to a container registry (the SCP-tarball model is a deliberate choice
  for this scale — see `workflows/README.md`).
- Multi-replica / orchestration (the `k8s/` manifests remain unused at single-VPS
  scale).
- Adding stateful services (would require revisiting the prune step).
